# Production deployment

Moved verbatim from AGENTS.md on 2026-11-26 to keep that file small. Record new decisions about this topic here; AGENTS.md holds only rules that apply to every task.

- Mirror first (user decision 2026-11-27): after the disk cleanup the server fetches the commit itself with `git fetch` through `https://gh-proxy.org/https://github.com/<repo>.git` into `refs/remotes/mirror/main`, giving up below 10 KB/s for 2 minutes or after 40 minutes. Only when that fails, or the commit is not there, do the checkout and the SSH batch push below run. A mirror failure must never fail the deploy: the former mirror `gh.gitwarp.top` was down from 2026-11-09 to 2026-11-15. When added, the proxy could not be reached from the user's PC, so it was untested from the server.
- SSH fallback in `.github/workflows/deploy-server.yml`: the GitHub runner checks out the commit, pushes it over SSH to a `deploy` transport branch in the server's `/opt/sida/app` repository, sending the new files first in batches of about 50 MB (`.github/scripts/push-in-batches.sh`, added 2026-11-24: the cross-border link once moved only 117 MB in 2 h 20 min, a 742 MB push could not finish inside GitHub's 6-hour job limit, and `git push` cannot resume; each batch is a parentless helper commit under `refs/deploy-batches/`, rebuilt identically on every run so a run that times out keeps the batches that arrived and the next run skips them, and the helper refs are deleted after the real commit arrives), fast-forwards the server's `main` to that exact commit, and rebuilds the Docker Compose `app` and `caddy` services. Before pushing it prunes dangling images and BuildKit cache unused for 24 hours; if under 10 GB is still free it then removes all unused BuildKit cache (`docker builder prune -af`, added 2026-11-21 after a day of many deploys left 44 GB of fresh cache and 2.4 GB free); then it stops if the server has under 3 GB free (a full 59 GB disk previously broke `git push`). Never add `--volumes` or `-a` image pruning there; `builder prune -a` touches only build cache. The server fetches only through the mirror above, never from github.com directly.
- Server disk and the Docker build (2026-11-27): the server disk is 59 GB, and the site's photos and videos (`xiaojuanschoolpayment.client/public`, 5.5 GB, of which 5 GB is 509 mp4 files) are stored once more by every Dockerfile step that copies them. The old Dockerfile kept five copies during a build (client source, Angular `dist`, the server build's `wwwroot`, the `dotnet publish` output and the runtime image), about 28 GB; with 29 GB free the last COPY failed with `no space left on device`, so every deploy failed although the site kept running the previous image. The Dockerfile now copies the Angular build straight into the runtime image's `wwwroot` (three copies, about 18 GB); the server only reads `wwwroot` from disk at run time (`UseStaticFiles`, `SpaSeoHtmlRenderer`, `FindStaticSiteIndex`), so `dotnet publish` does not need it. The deploy workflow removes all unused build cache when under 25 GB is free (it was 10). Each further GB of media needs about 3 GB of build space, so this fails again at roughly 9 GB of media; the lasting fix is to keep videos out of the image (object storage or a CDN, which the user postponed on 2026-11-26). Never put the client build back into the server-build stage.
