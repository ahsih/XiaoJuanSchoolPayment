# Production deployment

Moved verbatim from AGENTS.md on 2026-11-26 to keep that file small. Record new decisions about this topic here; AGENTS.md holds only rules that apply to every task.

- `.github/workflows/deploy-server.yml`: on every `main` push, the GitHub runner checks out the commit, pushes it over SSH to a `deploy` transport branch in the server's `/opt/sida/app` repository, sending the new files first in batches of about 50 MB (`.github/scripts/push-in-batches.sh`, added 2026-11-24: the cross-border link once moved only 117 MB in 2 h 20 min, a 742 MB push could not finish inside GitHub's 6-hour job limit, and `git push` cannot resume; each batch is a parentless helper commit under `refs/deploy-batches/`, rebuilt identically on every run so a run that times out keeps the batches that arrived and the next run skips them, and the helper refs are deleted after the real commit arrives), fast-forwards the server's `main` to that exact commit, and rebuilds the Docker Compose `app` and `caddy` services. Before pushing it prunes dangling images and BuildKit cache unused for 24 hours; if under 10 GB is still free it then removes all unused BuildKit cache (`docker builder prune -af`, added 2026-11-21 after a day of many deploys left 44 GB of fresh cache and 2.4 GB free); then it stops if the server has under 3 GB free (a full 59 GB disk previously broke `git push`). Never add `--volumes` or `-a` image pruning there; `builder prune -a` touches only build cache. The mainland-China server deliberately never fetches from GitHub or a third-party GitHub mirror; do not reintroduce a server-side `git pull`.
