# AI repository guide

This file applies to the whole repository. Read it before changing code. Keep it current when architecture, setup, routes, or deployment behavior changes.

## Product summary

XiaoJuanSchoolPayment is the codebase for **思达启航教育 (Sida Qihang Education)**, a Chinese-language education consultancy website. Despite the original project name, it is now broader than school payments. The public site markets and explains:

- Ireland undergraduate, postgraduate, foundation, visa, accommodation, and pre-departure services.
- Philippines English-study destinations, language schools, courses, accommodation, and fees.
- Online English courses, overseas study tours, guides, student feedback, and company information.
- School-specific quote calculators backed by database pricing.
- Contact and quote-image email forms.

There is also a JWT-protected employee area for maintaining schools, lessons, rooms, fees, notes, student applications, private documents, invitations, and uploaded school photos. Accounts register with a required email, an optional phone number, an access/invitation code, and a password; the configured access code always grants owner-level Admin while invitation codes carry their stored Staff (顾问), Manager (管理), or Student role. Login is password-only and accepts either the registered email or optional phone number. Password recovery accepts either identifier but always emails the reset link to the account's registered email.

## Architecture at a glance

```text
Angular browser app
  |-- public content and static assets
  |-- relative HTTP calls (/school, /auth, /contact-form, ...)
  v
ASP.NET Core API and static-file host
  |-- ASP.NET Identity + JWT roles
  |-- EF Core migrations and startup seed data
  |-- SMTP contact/quote delivery
  v
MySQL/MariaDB database
```

- Frontend: Angular 19, TypeScript 5.7, RxJS, Angular Material, Karma/Jasmine.
- Backend: ASP.NET Core 10, EF Core 9, Pomelo MySQL provider, ASP.NET Identity, JWT bearer authentication, Swagger.
- Production container: builds Angular with Node 22, publishes the .NET API, and serves the Angular build from `wwwroot` on port 8080.
- Development: Angular runs at `https://localhost:53747` and proxies API paths to the ASP.NET server, normally `https://localhost:7209`.

## Main data model and API behavior

`AppDbContext` extends `IdentityDbContext<SchoolUser>` and contains:

- `School`: parent record.
- `SchoolLesson`: course, duration in weeks, price, currency, description, and note.
- `SchoolRoom`: accommodation option, duration, price, currency, and description.
- `SchoolFee`: additional fee, currency, description, and last-updated time.
- `SchoolNote`: free-form school note.
- `SchoolPhoto`: school photo/video metadata. For COS-backed records `FilePath` is the object key and `Url` is the stable same-origin `/school/media-file/<id>` route; legacy/local records still point under `wwwroot/uploads/schools/<school-id>/`.
- `Currency`: code and symbol.
- `SchoolUser`: ASP.NET Identity user with first and last name. Admin accounts use the employee backend; Student accounts use the student portal.
- `InvitationCode`: single-use, expiring role invitation. Admin users create Staff/Consultant or Manager invitations; Manager and Staff users create Student invitations.
- `AccountVerificationCode`: legacy verification-code records retained for migration compatibility; the current authentication flow does not create or accept verification codes.
- `SchoolContentRevision`: per-school JSON snapshots for employee drafts and administrator-published website content, including version, author, change summary, and publish timestamps.
- `SchoolCommissionPolicy` and `SchoolCommissionRoomBasis`: private, structured partner-commission notices and room calculation bases. They are separate from public school content and readable only by Admin/Manager.
- `StudentApplication`: an internal registration dossier that supports a single student, a parent-child family, or a group of travellers. The primary contact owns the optional future Student-account link; additional members and independent multi-period course/accommodation plans are stored in structured versioned JSON while the legacy summary fields remain populated for list and portal compatibility. Enrollment date, overall enrollment status, and visa status are independent fields so staff can filter by signup month, not-yet-enrolled/enrolled/on-hold/cancelled records, and visa progress. Employees may create the dossier with only a primary name and school, add contact/study details later, and link the primary account automatically when a Student registers with the same email through a valid invitation. Employee changes are drafts with `Draft`/`PendingReview`/`Published` status; `PublishedSnapshotJson` preserves the last manager-approved student-visible version while a newer draft is edited or reviewed. One primary student can have multiple applications.
- `StudentApplicationDocument`: private application files such as quotes and offer letters. Files are stored outside `wwwroot` under `App_Data/student-documents`; additions and pending deletions follow the parent application's review workflow, and student downloads are limited to document IDs in the approved snapshot.
- `StudentPayment`: structured per-application payment records with amount, currency, payment type/date/method, receiving-account details, a private receipt file, submitter, and an independent `PendingReview`/`Confirmed`/`Returned` management-review workflow. Only confirmed student-visible payments appear in the student portal or count toward future receipt/payroll totals.

Key endpoint groups use route prefixes without `/api`:

- `/auth`: required-email/optional-phone registration, password login by email or phone, emailed password reset, password changes, and authenticated invitation management.
- `/school`: public read endpoints; legacy direct database writes are limited to Admin/Manager so Staff cannot bypass the revision review workflow. Staff may upload inactive media files for a content draft, while direct media mutation/deletion remains Admin/Manager-only.
- `/school-content`: anonymous published-content reads; Admin/Manager/Staff editor reads and draft saves. Staff/顾问 submits drafts with a required change summary for review. Admin/Manager may publish either their own `Draft` directly (also requiring a change summary) or a Staff `PendingReview`, and may return a pending review or restore a historical version. `/school-content/reviews` is the centralized Admin/Manager review queue and reports the school, submitter, timestamp, summary, and changed top-level content sections. Pricing, quote-image, and media editors use dedicated merge endpoints; published media visibility is synchronized only when a revision is published.
- `/internal-commission-policies`: Admin/Manager-only read access to private partner-commission policy records. No public, Staff, or Student endpoint exposes the policy or its room bases.
- `/staff-permissions`: owner-Admin-only employee role management plus the current Admin/Manager/Staff user's own permission view. Staff means 顾问 and may edit all schools and submit review but cannot publish; Manager means 管理 and may also review, publish, and return changes. Legacy `SchoolPermission` claims remain for compatibility but no longer restrict either employee type by school or feature.
- `/currency`: employee-only currency lookup.
- `/contact-form/send`: anonymous JSON contact submission through SMTP.
- `/quote-email/send`: anonymous multipart upload that emails a generated quote PNG.
- `/student-applications`: Admin/Manager/Staff may create an internal dossier using only a primary name and school, choose single/family/group registration, add up to 19 companions, and record multiple course and accommodation periods per person. Each period stores its start date and week count; the end date is normalized to `start + weeks × 7 - 1 day`, and list/portal summaries derive from the structured plans. Creating a dossier does not create a login account; an existing Student account with the same primary email is linked, and future invited Student registration links an unclaimed dossier by normalized email. The employee screen is an internal-first student workbench with attention filters, completion summaries, sectioned drawer editing, private application documents, and structured payment submission. Staff/顾问 submit each payment with amount, currency, date, method and receipt; Admin/Manager independently confirms or returns it, and `/student-applications/payment-reviews` feeds the centralized payment-review queue. Application content still follows its separate required-summary review flow: Staff submit, Admin/Manager publish or return. `/student-applications/reviews` feeds the application review queue, while `/student-applications/me` returns the last published application snapshot plus only currently confirmed payments. Private file downloads enforce employee access or matching Student ownership and approved visibility.
- `/pines-room-availability`: anonymous read-only PINES room availability feed; the server fetches fixed public school endpoints and returns only sanitized Main/IELTS dates, male/female vacancies, and exact continuous-stay options. The `/stay-options` child route supports the public room-plan calculator without exposing portal identifiers or navigation.
- `/exchange-rates/cny`: anonymous, cached (1 hour; 24-hour stale fallback) same-origin copy of the Frankfurter/ECB CNY rates in Frankfurter's `{ amount, base, date, rates }` shape. Only the WeChat mini program uses it, because a released mini program may call only ICP-filed domains; it applies the website's `exchange-rate-rules.ts` to the response. The website itself still fetches Frankfurter directly.
- `/uploads`: legacy static uploaded image and video files through ASP.NET static-file middleware. School media accepts JPG/PNG/WebP/GIF images up to 10MB and MP4/WebM/MOV/M4V videos up to 500MB; the authenticated multipart upload endpoint permits 512MiB for form overhead. Production COS uploads still pass through the app server and use temporary multipart storage, so monitor free disk space and transfer time for large videos.

The existing `/admin` area is the employee backend for Admin, Manager, and Staff roles. Staff is the 顾问 role: it has access to every school and editor, can save a draft and submit it with a required change summary, and can never publish. Manager is the 管理 role: it has the same editing access and may publish its own draft directly after supplying a required change summary; it also has `/admin/reviews`, where it can inspect school-content and student-application submissions before publishing or returning them. Publishing a school revision updates the website; publishing a student-application revision updates that student's portal, while the prior approved snapshot remains visible during review. Admin remains the owner role and can additionally invite employees and change an employee between Staff/Consultant and Manager; this type-based screen replaces the old per-school checkbox matrix. The home page school list follows the public Cebu directory's curated popularity order, leaves unranked schools alphabetized, and marks the top ten; keep that ordering synchronized when the public popularity list changes. `/admin/school-lessons?schoolId=<id>` opens the selected school's filtered course workspace; keep new employee content tools school-centric instead of restoring all-school edit tables. `/admin/school-content?schoolId=<id>` is the visual school-page editor: CIA, PINES, MONOL Main, MONOL Sparta, EV, EV Academy La Mer, SMEAG Capital, PHILINTER, CG Banilad, CG Sparta, CPI, B'Cebu, CPILS, GLC, I.BREEZE, A&J, IMS, BECI EOP/Sparta/City, JIC Challenger/Premium, IU, ICL, CELLA Uni Sparta/Premium, English Fella First/Second Campus, BTES, Cebu Blue Ocean, TARGET, and WALES are supported, and their same-origin iframes reuse the real public components for live previews. Their media tabs upload photo/video files as inactive records and store desired order/visibility in the versioned content draft; the public gallery/video area changes only when a revision is published. `/admin/school-quote-image?schoolId=<id>` supports the same schools and reuses the production canvas renderer for its preview. It edits headings, registration/course/accommodation copy, independent per-promotion notes, local-fee notes, calculated supplemental-fee explanations, service benefits, and footer notes; an explicitly empty saved value remains empty. CELLA campuses use separate school revisions, while English Fella keeps independent campus quote-image settings inside its shared school revision. Layout, branding, calculated prices, dates, promotion amounts, eligibility, and totals stay calculator-owned. Every editor surface follows the same split workflow: Staff saves a draft and submits it with a required change summary; Admin/Manager can instead publish their own draft directly with the same audit note, or approve/return a Staff submission. `/student` is the Student-role portal. Admin users create single-use Staff/Consultant or Manager invitations, and Staff/Manager users create single-use Student invitations from `/admin/invitations`. Invitees register a required email, an optional phone number, an access/invitation code, and a password. They can log in with their email or registered phone number and password. Password recovery accepts either identifier and sends the reset link only to the registered email through the `ContactForm` SMTP configuration. The configured `AccessCode` can register an Admin at any time; keep it secret because possession grants administrator-registration authority. Configure `Authentication__PublicOrigin` in production so emailed password-reset links use the canonical public site origin. Keep student documents out of public static-file folders. `StudentDocuments__RootPath` can point document storage at a persistent mounted directory in production; the default is `App_Data/student-documents` under the server content root.

The Angular services use relative URLs so the development proxy and production same-origin hosting both work. Preserve this unless deployment is intentionally changed.

The supported visual editors and embedded public pages use a same-origin, source-checked preview-message handshake. Selecting an item or focusing its form field reveals the real public section (including nested disclosures), scrolls only the iframe, and keeps an orange highlight; clicking a preview item selects its form. Tab changes must not reload the iframe or reset the quote scenario. Hidden items and inapplicable promotions fall back to their section with an explicit status message. Preview annotations never appear on the normal public page. Focused CIA navigation tests run with `npx ng test --watch=false --browsers=ChromeHeadless --ts-config=tsconfig.cia-preview-spec.json --include=src/app/pages/philippines/cia-school/cia-content-preview.spec.ts`; PINES calculation/component tests use `tsconfig.pines.spec.json`, MONOL tests use `tsconfig.monol.spec.json`, I.BREEZE tests use `tsconfig.ibreeze.spec.json`, A&J tests use `tsconfig.anj-spec.json`, and JIC quote-rule tests use `tsconfig.jic.spec.json`.

IU and ICL are also supported by both unified employee editors. Their independent versioned content documents drive each public page, calculator, local-fee table, generated quote image, and real-page editor preview without sharing prices or room-opening rules.

## Local setup

Prerequisites:

- Node.js 22 and npm.
- .NET 10 SDK.
- MySQL 8 or a compatible MariaDB instance.
- A trusted ASP.NET development HTTPS certificate (`dotnet dev-certs https --trust`) if using HTTPS locally.

Install the client dependencies:

```powershell
cd xiaojuanschoolpayment.client
npm ci
cd ..
```

Configure secrets outside source control. ASP.NET Core environment variables use double underscores for nested keys. A minimal PowerShell example is:

```powershell
$env:ConnectionStrings__DefaultConnection = "server=localhost;port=3306;database=SchoolPayment;user=<user>;password=<password>"
$env:Jwt__Key = "<long-random-development-key>"
$env:Jwt__Issuer = "SchoolPayment"
```

## Security and deployment cautions

- Every push to `main` deploys production through `.github/workflows/deploy-server.yml` (disk cleanup, runner-to-server SSH `git push`, fast-forward, `docker compose --env-file /opt/sida/.env -f compose.production.yml up -d --build app caddy`). The runner pushes the commit to the server over SSH, and the server then runs `docker compose --env-file /opt/sida/.env -f compose.production.yml up -d --build app caddy`; see the repository map entry above. The server never pulls from GitHub: its former mirror `gh.gitwarp.top` returned HTTP 523 from 2026-11-09 until the 2026-11-15 workflow fix. Caddy is the reverse proxy. `compose.production.yml` and `.env` exist only on the server, so a change that requires a new setting must fail safe rather than crash startup.
- Git history still contains a former JWT key, administrator `AccessCode`, local database values and a Gmail SMTP app password. Never quote those values in tickets, prompts, logs, or documentation. `Services/Security/AuthSecrets.cs` (`RevokedSecrets`) rejects the former JWT key and access code by SHA-256 hash, so they never authenticate again even if copied into an environment. The SMTP password must be revoked at its provider; code cannot revoke it.
- JWT signing uses the single `JwtSigningKey` singleton. A missing, shorter-than-32-byte or revoked `Jwt:Key` falls back to a random per-process key and logs a critical warning; the site keeps running but every restart signs users out. Tokens default to 7 days (`Jwt:ExpiresInMinutes`, clamped to at most 30 days) and carry a SHA-256 hash of the Identity security stamp (claim `sstamp`) that `JwtSecurityStamp.ValidateAsync` checks against the database on every authenticated request. Password change/reset and employee-type changes rotate the stamp and revoke older tokens; `/auth/change-password` returns a replacement token. The Angular `AuthSessionInterceptor` clears the stored session and routes to `/login` when a request that carried a bearer token receives 401.
- `AccessCode` grants Admin registration whenever supplied and must be protected as an administrator credential. It is compared in constant time, and a revoked or empty value disables access-code registration. Registration codes are HMAC-hashed and invitations are SHA-256-hashed in storage.
- The canonical public origin `https://sidaqihang.com` is committed in `appsettings.Production.json` (not a secret; `Authentication__PublicOrigin` still overrides it). Password-reset links use only `Authentication:PublicOrigin` outside Development. Without it, `/auth/forgot-password` returns 503 and logs an error rather than trusting the request Host header. Sitemap/robots URLs also prefer the configured origin.
- `Services/Security/AbuseRateLimits.cs` applies per-client fixed-window limits: quote email 10 per 10 minutes, contact form 5 per 10 minutes, and login/register/forgot/reset password 20 per 5 minutes, all returning 429 with a Chinese message. `X-Forwarded-For` is trusted only from loopback/private peers (Caddy), using its last entry. `OutboundMailThrottle` additionally caps actually sent anonymous mail site-wide at 30 quote emails and 20 contact forms per hour. Quote email accepts only PNG signatures.
- CORS still allows any origin and should be restricted to trusted production domains before exposing the API publicly.
- Swagger is enabled only in Development.
- The Docker image does not contain MySQL; supply `ConnectionStrings__DefaultConnection` at runtime.
- With `TencentCos__Enabled=true`, new school photos and videos are written to the configured private COS bucket; keep its credentials out of source control and grant only the required object permissions for the `school-media/` prefix. Existing local records continue to be served from `wwwroot/uploads`, so preserve or migrate that directory before removing its production volume. Without COS enabled, all new school media still uses local storage and therefore requires a persistent mount.
- The GitHub Pages workflow deploys only static frontend files. Same-origin relative API requests will target GitHub Pages and fail unless a backend/base-URL strategy is added.
